# MeshTree — Agent Working Contract

All AI agents working in this repository (IDE orchestrator or terminal CLI) follow these rules without exception.

## Standing orders

1. `SPEC.md` is the authoritative specification. Never contradict it. If you believe the spec is wrong or incomplete, stop and propose a change in `docs/adr/` instead of silently deviating.
2. Work one task at a time from `docs/tasks/backlog.md`: at the start of every session, read `docs/tasks/backlog.md` and `docs/tasks/PROGRESS.md`, pick the lowest-numbered task whose status is `todo` and whose `Deps` are all `done`, and work only that task.
3. Never modify code outside the task's stated `Scope` fence, and verify the work against the task's `Authority: SPEC §x` citations. Do not refactor, reformat, or "improve" unrelated modules.
4. A task may move to `done` only when all four verification commands pass locally and the 3-OS CI matrix is green:
   - `cargo fmt --all --check`
   - `cargo clippy --workspace -- -D warnings`
   - `cargo build --workspace`
   - `cargo test --workspace`
5. Commit per task with the message `T-0XX: short summary`. Keep diffs reviewable by a human in one sitting. Commits must strictly be authored and committed by the configured repo user (`Lucas Pan <109758310+Aviation-0@users.noreply.github.com>`). Never append `Co-authored-by:` trailers or inject agent attribution into commit messages.
6. Before ending any session, update both `docs/tasks/backlog.md` and `docs/tasks/PROGRESS.md` (milestone counts, current focus, next up), append a dated handoff entry under `## Handoff log` in `docs/tasks/backlog.md` (current task, state, what's done, what's next, failing tests if any), and commit.
7. CI runs on a 3-OS matrix (Linux, macOS, Windows). Never push with failing CI. Windows-specific behavior must be written for Windows, not ported blindly from Unix.
8. Prefer stdlib and small, well-maintained dependencies. Any new dependency requires a one-line justification in the commit message.
9. Update task statuses (`todo` / `doing` / `blocked` / `done`) in `docs/tasks/backlog.md` and milestone counts in `docs/tasks/PROGRESS.md` as you work.
10. When uncertain between two implementations, choose the one that is easier to test deterministically.
